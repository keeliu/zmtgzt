# Design

## Context

三个问题中，两个是**已定位的实现缺陷**（二维码未渲染 + 失败被吞；`window.prompt` 在
Electron 不可用），一个是**能力缺口**（公众号第二条登录路径未暴露）。
本设计记录修复与实现过程中的关键取舍。

约束：

- 上游脚本的行为不可改（`vendor/easel/` 是同步来的快照，改了就与上游漂移）。
- 登录态真相源是 `~/.easel-browser-profiles/`，插件不另建存储。
- 公众号配置文件位置由上游 `config.py::_config_path()` 固定，只查
  `skill-wechat-publisher/wechat-publisher.yaml`。

## Decisions

### D1：二维码经 HTTP 端点传输，不在响应体里内嵌 base64

插件新增 `GET /api/zmtgzt/account/login/qr?channelId=<id>`，直接返回 PNG 字节流。

**理由**：状态轮询是高频的（每 2 秒一次），若把图片 base64 放进状态 JSON，
每轮都要重复传输几十 KB；而浏览器对 `<img src>` 有缓存与按需加载。
用独立端点还能让「图片存在与否」与「状态」解耦——状态说 `qr_ready` 而文件尚未落盘时，
端点返回 404，前端据此不渲染破图。

**替代方案**：状态 JSON 内嵌 base64。被否：轮询成本高，且状态文件由上游
`write_status` 写入，其 `qr` 字段约定是**路径**而非内容（见 `login_state.py`），
内嵌需要插件改写上游协议。

### D2：把「预检」提到发起登录之前

`cmd_login` 的第一行就可能因缺 `playwright` 直接退出，且**在写任何状态之前**。
因此插件侧先做探测：Python 可执行、`playwright` 可导入、`cv2` 与 `PIL` 可导入。

**理由**：与其启动一个注定失败的进程、让用户对着 `unknown` 猜，不如先探测并给出
确切的缺失项与安装命令。预检本身也是一次 Python 调用（`-c` 逐项 import）。

**注意**：预检结果 SHALL NOT 被长期缓存——用户装完依赖应当立即生效，
故每次发起登录前重新探测。

### D3：日志按渠道单文件、覆盖式留存

每次登录把 stdout/stderr 重定向到 `<dataDir>/login/<channelId>.log`，覆盖上一轮。

**理由**：排障只需要最近一次；无上限增长会污染数据目录。
`stdio` 从 `'ignore'` 改为写文件描述符，同时仍保持 `detached` 以便登录流程
不阻塞请求。

**同时**：必须监听子进程 `error` 事件——旧实现漏了这一处，
解释器路径不存在时 Node 会抛未捕获异常。

### D4：内联表单，而非引入模态组件库

新建画像 / 新建主题 / 删除确认都改为界面内的展开式输入与二次确认态。

**理由**：`window.prompt` 在 Electron 返回 `null` 且不显示（这是本次「点击没反应」的
直接原因）。而引入模态组件库会带来额外依赖与主题适配成本。
内联表单天然融入现有布局、复用已有的主题令牌样式、并且能就地显示服务端返回的
校验错误（例如主题名不合法的原因）——这是原生 `prompt` 做不到的。

### D5：公众号 YAML 用「保留原行 + 字段级补丁」写入

不整体重写文件。算法：

1. 读原文件为行数组
2. 定位 `accounts:` 行；在其下按缩进定位目标账号键
3. 目标账号块内：已存在的字段行**就地替换值**，缺失的字段**在该块末尾插入**
4. 目标账号不存在时，在 `accounts:` 块末尾追加完整块
5. `default:` 行已存在则更新，否则在文件头部插入
6. **其余行完全不动**

**理由**：规范要求「保留其它账号与其它字段」。整体重写会丢掉用户手工添加的注释、
其它顶层配置（如 `image_generation`、`integrations`，见上游 `config.py` 会读取这些键）。
行级补丁是唯一能同时满足「准确改目标字段」与「不动其余内容」的做法。

**兜底**：写入前将原文件复制为 `<file>.bak`；解析异常时直接报错而不写入，
避免半损坏状态。

### D6：凭证校验走官方 `cgi-bin/token`，并区分 `40164`

提交凭证后调用：

```
GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=..&secret=..
```

按返回区分：成功 / `40001`·`40002`（凭证错）/ `40164`（IP 未白名单）/ 网络不可达。

**理由**：`40164` 意味着**凭证本身正确、问题在出口 IP 未登记**。若把它归为
「凭证错误」，用户会反复核对 AppID/Secret 而找不到原因——这是最容易浪费时间的误判。
微信错误码语义见上游 `skill-wechat-publisher/references/errors.md`。

### D7：AppSecret 不回传前端

读取配置的接口只返回「是否已配置」+ AppID 脱敏形式 + 账号键，不回传完整 AppSecret。

**理由**：前端展示无需要明文；一旦回传，它会进入浏览器内存与可能的日志。
**如实说明**：按上游约定，AppSecret 在 `wechat-publisher.yaml` 中是**明文存储**的，
这是微信官方 API 的常见做法，非本插件引入的风险，但用户应当知情。

### D8：有头登录与 headless 并列，不替代

`xhs_publish.py login --headed` 会弹出真实浏览器窗口供用户扫码/短信登录。

**理由**：headless 抠图依赖 `cv2` 识别二维码，在某些页面结构下会识别失败
（上游 `capture_qr` 会抛「未找到可识别的登录二维码」）。有头模式是可靠的兜底。
两者并列由用户按环境选择，而不是自动切换——因为纯服务器环境没有桌面，自动切过去只会失败。

## Risks

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Python 依赖缺失（playwright / opencv / Pillow） | 登录完全不可用 | D2 预检前置，给出确切缺失项与安装命令 |
| 二维码有时效（约几分钟） | 扫码失败 | 状态过期后提示重试；提供重新发起入口 |
| 复合结构的 YAML 解析失败 | 误改用户配置 | D5 的行级补丁不做全文件重写；写入前 `.bak` 备份；解析异常即报错不写入 |
| 微信接口网络不可达（含代理场景） | 无法校验凭证 | 区分「网络问题」与「凭证错误」；提示检查网络/代理 |
| 出口 IP 未白名单（`40164`） | 校验失败但凭证正确 | D6 单独提示，明确说明是白名单问题 |
| AppSecret 明文落盘 | 泄露风险 | 属上游既有约定；D7 不回传前端；文档中如实告知 |
| 有头模式在无桌面环境启动失败 | 用户困惑 | 界面说明该方式的适用条件 |
| 轮询无限进行 | 前端资源占用 | 状态机驱动，`success`/`expired`/`error` 一律终止轮询 |

## 未决与边界

- **短信验证码回填**：上游状态机含 `sms_required`（扫码后风控要求短信验证），
  其 `read_sms_code` 约定从 `outputs/_login/<platform>.code` 读取。
  本变更**只呈现该状态并提示**，不实现验证码回填写入——需要确认交互形态后再做。
- **今日头条**：上游未实现，维持「暂不支持」，不在本变更范围内。
