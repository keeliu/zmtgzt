# Design

## Context

目标：让「在 dsh 里把内容发到小红书」成为可用能力，并顺带覆盖公众号。
约束：上游脚本与 `vendor/easel/` 快照不改动；门禁不提供绕过开关；
发布是对外不可逆动作，默认必须保守。

## Decisions

### D1：布尔参数映射为裸 flag，而不是「flag + 值」

```ts
if (typeof value === 'boolean') {
  if (value) out.push(`--${key}`)   // 只输出 flag
  continue                          // false 直接跳过
}
```

**理由**：argparse 里 `store_true` / `store_false` 表达的是「有无该 flag」。
实测 `--exec true` 会被解析为多出的位置参数并报 `unrecognized arguments: true`，
命令直接失败。小红书发布必须 `--exec`，所以不修这个就永远发不出去。

**被否方案**：在工具层要求调用方传 `exec: ''` 或 `exec: 'yes'` 之类的技巧。
治标不治本，且会让每个 flag 都变成「要记住特殊写法」的坑。

**注意**：该修复同样解锁 `--headed`（窗口登录）、`--no-proxy`、`--official-api` 等，
属于全局性修复。

### D2：一个 `zmtgzt_publish` 工具覆盖多平台，而不是每个平台一个工具

用 `platform` + `type` 参数分派到对应脚本与子命令。

**理由**：两个平台的发布流程是同构的（预检 → 门禁 → 确认 → 执行 → 留痕），
差异只在于脚本映射与少数参数。集中在单个工具里可以让门禁顺序、dry-run 语义、
留痕逻辑只有一份实现，避免两处漂移。

**被否方案**：`zmtgzt_publish_xhs` / `zmtgzt_publish_wechat` 两个工具。
门禁与确认逻辑会被复制两份，且平台矩阵继续扩大时工具数线性增长。

### D3：默认 dry-run，确认走独立参数

工具默认只预检；真实发布需要一个显式的确认参数（且在描述里写明后果）。

**理由**：发布是对外不可逆动作。默认安全，让「误调用」不会产生对外影响。
这也与上游一致——`xhs_publish.py` 与 `publish.py` 都要 `--exec` 才真发。

### D4：门禁顺序固定为「硬门禁 → 人设提醒」

1. `content_guard.py`：检出内部信息泄露（API Key / 内部 URL / 代理 IP / 模型名）
   → **真实发布阻断**
2. `persona_gate.py`：人设一致性 → **只提醒，不阻断**

**理由**：这是 AGENTS.md 规定的顺序与强度差异。内容安全是硬约束（泄露即事故），
人设只是创作质量问题。把两者强度颠倒会让插件既危险又难用。

### D5：不暴露绕过门禁的开关

上游有 `--allow-unsafe` 与 `--skip-ai-score`，插件在工作台**不提供入口**，
工具描述也不把它们列为首选参数。

**理由**：门禁的价值在于默认生效。把这些开关摆到界面上，等于把「一键跳过安全检查」
做成常规操作。需要时仍可在对话里显式调用通用执行器并说明理由——保留能力，
但不降低操作摩擦到「顺手就过了」。

### D6：媒体从主题产物中选取，而不是手填路径

发布页从所选主题的 `outputs/<主题>/` 列出媒体文件供勾选。

**理由**：实测脚本会校验路径存在性（`ERROR: 文件不存在：...`）。
让用户手打路径必然出现拼错与相对路径问题；从产物里点选既避免这类错误，
也把「主题 → 产物 → 发布」串成一条可追溯的链路。

### D7：公众号默认走后台会话，官方 API 作为可选路径

`publish.py` 默认 `session_mode=True`，`--official-api` 才切到官方 API。

**理由**：后台会话免 AppID/AppSecret、免 IP 白名单，摩擦最低；官方 API 需要凭证
加白名单。默认值与上游一致，也与「两条路都能用、用户按条件选」的既有设计一致。

### D8：公众号结果表述为「草稿已创建」而非「已发布」

`weixin_mp_stats.py publish` 的注释写明「建草稿」，`publish.py --exec` 的帮助文本是
「确认创建微信草稿」。也就是说**这两条路径都不群发**，用户仍需到后台手动群发。

**理由**：把「创建草稿」说成「已发布」是事实错误，会让用户以为内容已经对外可见。
界面必须在结果里明确区分，并给出后续步骤。

### D9：二次确认用界面内确认态

与上一轮修掉 `window.prompt` 的理由相同：`window.confirm` 在 Electron 中不可靠。
确认文案必须说明「发布到公开平台」或「创建草稿」以及不可逆性。

## Risks

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 平台风控/限流/封号 | 账号受损 | 上游 SKILL 明确警告；插件在界面呈现该提示并建议先用测试号、小流量、人工复核。**不代为承担风险，也不隐藏警告** |
| 未登录即发布 | 发布失败 | 脚本返回明确错误；工具转发原因并指向账号页 |
| 媒体路径错误 | 发布失败 | D6 从产物选取 + 提交前存在性校验 |
| 登录目录被占用（profile lock） | 发布失败 | 脚本已有 90s 锁等待并返回明确错误，插件如实转发 |
| 出口 IP 被平台判风险（小红书） | 登录/发布被拦 | 属网络环境问题；界面提示需要干净网络/家宽代理 |
| 公众号 AI 味检测达阈值 | 草稿创建被阻止 | 默认行为，如实返回原因（阈值可配于账号配置） |
| 沙箱环境无法端到端验证真实发布 | 未经真实账号验证 | 测试覆盖参数装配、dry-run、门禁顺序、错误分支；**真实发布在 tasks.md 中如实标注未验证** |
| 发布脚本依赖 playwright | 依赖缺失时失败 | 复用上一轮的环境预检；发布前同样可预检 |

## 未决与边界

- **多平台同步**（`--sync`，需 Wechatsync CLI 与 token）：上游标注为可选且当前环境不可用，
  本变更不暴露。
- **公众号群发**：上游不提供，本变更不新建实现。
- **定时发布**：不属本变更范围。
